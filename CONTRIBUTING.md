# Contributing to rDownloader

Thank you for taking the time. Bug reports, ideas, plugins and code are all welcome, and this page
explains how each of them reaches the project.

## How this repository works

This GitHub repository is an **export** of a private development repository. It is refreshed at
every release as one fresh commit, without the development history. That has one consequence
worth knowing before you open a pull request:

**A pull request here is a proposal, and it is closed rather than merged.** When a change is
accepted, the maintainer applies it by hand in the development repository and credits you in that
commit — as `Co-authored-by` with your GitHub noreply address, or however else you prefer; say so
in the pull request. The pull request is then closed with a pointer to the release that carries
your change. A closed pull request therefore does not mean a rejected one: the comment on it says
which it was.

Issues work as usual and are the best place to talk about a change before you write it.

## What helps most

- **Bug reports.** Use the bug report form. The version (Settings → About rDownloader, or
  `rdownloader --version`), the platform, how you installed it and the steps that lead to the
  problem make the difference between a fix and a guess.
- **A diagnostic bundle.** The *Logs* page builds one on your machine, after showing you exactly
  what it will contain ([Diagnostics and maintenance](https://github.com/degoya/rDownloader/wiki/diagnostics-and-maintenance)). Credentials are redacted
  before anything is stored, but the bundle still describes your setup — hosts, paths, plugin
  names. **Look through it before you attach it to a public issue**, and untick or remove
  anything you would rather not publish.
- **Feature ideas.** Use the feature request form and describe the problem you want solved, not
  only the solution you have in mind.
- **Plugins.** Support for a new hoster, protocol, notifier or storage target does not have to
  live in this repository. Third-party plugins are signed WebAssembly components built with the
  SDK in [`sdk/`](sdk/) and published from their own repositories. The handbook's
  [Developing a plugin](https://github.com/degoya/rDownloader/wiki/developing-a-plugin) and [Plugin reference](https://github.com/degoya/rDownloader/wiki/plugin-reference)
  describe the manifest, the capabilities and how packages are signed and installed.

## Security issues

Please **do not** report a vulnerability in a public issue or pull request. Use GitHub's private
vulnerability reporting instead, as described in [SECURITY.md](SECURITY.md):
<https://github.com/degoya/rDownloader/security/advisories/new>.

## Building and testing locally

[Building from source](https://github.com/degoya/rDownloader/wiki/building-from-source) in the handbook covers the prerequisites,
building for every platform, the plugin components and the quality checks. `scripts/check.sh` runs the checks that matter for
your change — formatting, Clippy, the Rust tests, the SQLx query cache, the web type check and
tests — and prints what it skipped and why; [`scripts/README.md`](scripts/README.md) describes
its options. Please say in your pull request which checks you ran.

## Conventions that matter in a pull request

These are the conventions a contribution most often runs into:

- **Rust sources are English-only** — comments, identifiers, test strings and commit messages.
  `crates/rdownloader/tests/no_german.rs` fails on an umlaut or sharp s in a `.rs` file.
- **No `.unwrap()` outside tests.** Clippy warns on `unwrap_used` and the checks run with
  `-D warnings`; `unsafe_code`, `dbg!` and `todo!` are denied outright.
- **Every UI string exists in all four languages** (`web/src/locales/{de,en,es,fr}/`). Add a key
  with `scripts/i18n-key.sh <catalogue> <key> <de> <en> <es> <fr>`, which writes all four at
  once; changing a key means changing all four.
- **Errors carry stable codes, not free text.** A REST error returns a `code` that the web
  interface translates; user-facing text never lives in Rust as prose.
- **Generated files are regenerated, never edited by hand.** After a REST or DTO change, run
  `scripts/api-contract.sh`, which rewrites `web/openapi.json` and `web/src/api/schema.d.ts`.
  `web/components.d.ts` and `web/auto-imports.d.ts` are generated by the web tooling as well.
- **Keep a change focused.** One fix or one feature per pull request is far easier to review and
  to carry over by hand than a mix. Add a line to `CHANGELOG.md` under `[Unreleased]` and update
  the documentation the change affects.
- **No secrets or personal data** in code, tests, fixtures or screenshots — no real account
  names, tokens, cookies or download links you are not entitled to share.
